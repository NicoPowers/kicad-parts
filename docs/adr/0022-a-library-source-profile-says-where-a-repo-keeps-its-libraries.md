# A library source profile says where a repo keeps its libraries

The person designs for many clients, and each client is a team with a library repo (ADR 0021). Each client's repo is laid out its own way. Models sit next to footprints or in a folder of their own, lib tables are in the repo or not, path variables have the client's own names, and some have a `.kicad_dbl`. Later work browses, checks, writes and imports these libraries (kicad-parts-02fb, kicad-parts-ff3c, kicad-parts-92cb). So the app keeps, for each repo, a library source profile: where its libraries, 3D models and path variables are. Decided 2026-10-24 by best judgement (kicad-parts-e9a3, which took over kicad-parts-e83f).

- **The profile.** For one repo at one commit: its symbol libraries and footprint libraries (nickname and path in the repo), its model folders, its path variables (name and the repo folder each points to), its `.kicad_dbl` files, and a short prefix. Paths are repo paths with `/`, matched with exact case, so a profile means the same on Windows, macOS and Linux. The type is `SourceProfile` in `crates/kicad-integration/src/library_source.rs`.
- **Our own layout is the default profile.** `SourceProfile::own()` says every `.kicad_sym` in `symbols/` and every `.pretty` in `footprints/` is a library named by its file, models live in `3d-models/`, and `${GITPLM_PARTS}` points to the repo's top folder. The library check, the import, Add part, choosing from our libraries, the Libraries browser, the 3D view and the resolver read our libraries through it. It is the one place that spells out those folders. Every library check, pilot and full-pilot result stayed the same, byte for byte.
- **Never rename what boards use.** A client's boards store the client's own nicknames, so nicknames stay exactly as the repo's lib tables, or else its file and folder names, give them. The prefix (by default the team's code, such as `AC`) only tells sources apart inside the app, such as in the Libraries browser. It names only libraries the app itself makes later. The UI calls it the short name in this app.
- **The scan.** It runs on the app's own copy at the latest commit of the main branch, through `LibraryRepo::list_files` and one batch read, never on the person's checkout. It finds `.kicad_sym` files, `.kicad_symdir` and `.pretty` folders, 3D models (`.step`, `.stp`, `.stpz`, `.wrl`, `.wrz`), lib tables and `.kicad_dbl` files. Nicknames come from the repo's lib tables, read with `lib_table.rs`'s parser; `${KIPRJMOD}` is the table's folder. A path variable's folder is the one whose files match the most links that use it, from footprints' 3D model links and lib table rows. KiCad's own variables and `${KIPRJMOD}` in a model link are not the repo's.
- **Doubts.** The scan lists what the person should check: a link to a missing 3D model, a link whose file differs only in capitals (it works on Windows and macOS, not on Linux), two libraries with one nickname, a variable with no matching folder, a file stored with Git LFS, and a lib table that can't be read. A Git LFS pointer is reported, never read as a model; full Git LFS support is kicad-parts-fdb6.
- **One screen to confirm.** After linking, the team's row offers "Review library layout". The screen shows counts, what to check, the short name, each path variable with its folder, the model folders, and the libraries. The person changes only the short name, a variable's folder, or a library to leave out, then chooses "Use this layout". "Scan again" fetches first, and scans the app's copy as it is while the host can't be reached.
- **Where the profile lives.** In `library-layouts/<copy's folder name>.json` in the local data folder, beside `library-repos/`. One small file per repo, written through a temporary file. It holds the commit, a fingerprint of that commit's scan, the person's choices and the profile; no secrets. The file goes when no team links the repo any more.
- **Following the main branch.** After each fetch, a newer commit is scanned again. If the scan is the same (libraries, model folders, variables, tables and doubts, not how many files), the profile moves to that commit silently. If it differs, the row says "The library changed since you reviewed it." and offers "Review again". The layout reviewed before stays in use meanwhile.
- **The Libraries browser.** Each linked team's reviewed libraries form a group after ours, with the team's mark and the repo's name. They are written out of the copy into `library-layouts/<repo>.files/<commit>/`, once per commit, so the browser and kicad-cli read files. This works offline. 3D models stay in the copy.
- **The resolver.** A reference `LIB:NAME` is looked up in a profile, then in KiCad's bundled libraries. For a client repo the profile's libraries come from the repo's lib tables, so a nickname that differs from its file name finds the library KiCad would. The file a table row names is matched with exact case.

## Considered options

- **Rename client libraries with the prefix, such as `AC-Passives`.** Rejected: the client's boards store the old names and would break.
- **Scan the person's own checkout.** Rejected: it may hold changes not committed, and the app never reads or writes a person's work (mx-70700f).
- **Ask the person to describe each repo by hand.** Rejected: most repos scan right, and hardware engineers should only fix what the scan got wrong.
- **Read the person's own KiCad lib tables for a client repo.** Not now: they describe one computer, not the repo. The resolver still does not read them; see Consequences.
- **Keep profiles on the team server.** Later: sharing profiles with teammates through the team server is a next step.

## Consequences

- `crates/catalog-browser/src/library_repos/layout/` holds the scan (`scan.rs`, one pure function over a file list and some bytes), the store (`store.rs`), the browser's files (`files.rs`) and `Layouts`, which `LibraryRepos` uses.
- The library check and Add part still read only our own layout, through the default profile. kicad-parts-02fb and kicad-parts-ff3c extend them to client profiles. Choosing an item for a part leaves team groups out until copying between teams arrives (kicad-parts-1a46).
- `models_by_library` says where a footprint's own 3D model goes; only our layout has one. kicad-parts-02fb works out such rules for client repos.
- The import's own reading of model links (`classify_model_reference`) still follows the CSV catalog oracle, and keeps reading the older `${GITPLM_3DMODELS}` name. The library check does not, as before.
- **Known gaps:** the scan does not check a model link through `${KIPRJMOD}` or an absolute path. A lib table row whose path leaves the repo is skipped. The resolver does not read the person's own lib tables, so a person's table that remaps a KiCad nickname is still not followed (kicad-parts-e83f).

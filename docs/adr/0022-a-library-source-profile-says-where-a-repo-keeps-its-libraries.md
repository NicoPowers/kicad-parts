# A library source profile says where a repo keeps its libraries

The person designs for many clients, and each client is a team with a library repo (ADR 0021). Each client's repo is laid out its own way. Models sit next to footprints or in a folder of their own, lib tables are in the repo or not, path variables have the client's own names, and some have a `.kicad_dbl`. Later work browses, checks, writes and imports these libraries (kicad-parts-02fb, kicad-parts-ff3c, kicad-parts-92cb). So the app keeps, for each repo, a library source profile: where its libraries, 3D models and path variables are. Decided 2026-10-24 by best judgement (kicad-parts-e9a3, which took over kicad-parts-e83f), and changed the same day after review.

- **The profile.** For one repo at one commit: its symbol libraries and footprint libraries (nickname and path in the repo), its model folders, its path variables (name and the repo folder each points to) and its `.kicad_dbl` files. Paths are repo paths with `/`, matched with exact case, so a profile means the same on Windows, macOS and Linux. The type is `SourceProfile` in `crates/kicad-integration/src/library_source.rs`, which also holds the only helpers that turn repo paths into plain paths and paths on this computer.
- **Our own layout is the default profile.** `SourceProfile::own()` says every `.kicad_sym` in `symbols/` and every `.pretty` in `footprints/` is a library named by its file, models live in `3d-models/`, and `${GITPLM_PARTS}` points to the repo's top folder. Its `own_library_start`, `g-`, says how the libraries the app makes are named. The library check, the import, Add part, choosing from our libraries, the Libraries browser, the 3D view and the resolver read our libraries through it. It is the one place that spells out those folders. Every library check, pilot and full-pilot result stayed the same, byte for byte. KiCad's installed libraries have a small definition of their own, `SourceProfile::kicad_installed()`.
- **Never rename what boards use.** A client's boards store the client's own nicknames, so nicknames stay exactly as the repo's lib tables, or else its file and folder names, give them. The first plan had a short prefix per repo for telling sources apart inside the app. Nothing used it, so it was dropped: the Libraries browser marks each repo with its team's mark. Naming the libraries the app makes for a client repo is for kicad-parts-02fb, starting from the team's code.
- **The scan.** It runs on the app's own copy at the latest commit of the main branch, through `LibraryRepo::list_files` and batch reads of at most 16 MB, never on the person's checkout. It keeps only lib tables and each footprint's model links, so a large library never sits in memory whole. It finds `.kicad_sym` files, `.kicad_symdir` and `.pretty` folders, 3D models (`.step`, `.stp`, `.stpz`, `.wrl`, `.wrz`), lib tables and `.kicad_dbl` files. Nicknames come from the repo's lib tables, read with `lib_table.rs`'s parser; `${KIPRJMOD}` is the table's folder, and a row may climb with `..` inside the repo. A path variable's folder is the one whose files match the most links that use it, from footprints' 3D model links and lib table rows. A model link never climbs with `..`. KiCad's own variables (`KICAD<n>_*`, `KISYS*`) and `${KIPRJMOD}` in a model link are never the repo's.
- **Doubts.** The scan lists what the person should check, in plain words: a link to a missing 3D model; a link whose file differs only in capitals (it works on Windows and macOS, not on Linux); two libraries with one nickname; a variable with no matching folder; a file stored with Git LFS; a lib table that can't be read; an old-format `.lib` symbol library, which KiCad can convert; a footprint outside any `.pretty` folder, whose links still count; links through KiCad's own folders other than its 3D models, such as `${KICAD8_3RD_PARTY}`; a footprint or table over 4 MB, left unread; and a library file whose name Windows can't keep (a device name such as `CON` or `com1.txt`, or one ending in a dot or space), left out. A Git LFS pointer is reported, never read as a model; full Git LFS support is kicad-parts-fdb6.
- **One screen to confirm.** After linking, the team's row offers "Review library layout". The screen shows counts, what to check, each path variable with its folder, the model folders, and the libraries. The person changes only a variable's folder or a library to leave out, then chooses "Use this layout". Where two libraries share a nickname, the review first keeps the one a lib table names, else the first, and refuses to save with both kept, saying which: KiCad would use only one. "Scan again" fetches first, and scans the app's copy as it is while the host can't be reached. "Use this layout" reuses the scan the screen showed.
- **Where the profile lives.** In `library-layouts/<key>.json` in the local data folder, beside `library-repos/`; the key is the start of the SHA-256 of the copy's folder name, short to stay clear of Windows' path length limit. One small file per repo, written through a temporary file. It holds the commit, a fingerprint of the reviewed scan, the person's choices, the profile and the newest commit scanned since; no secrets. A saved choice whose variable, folder or library is gone at a later commit is dropped. The file goes when no team links the repo any more.
- **Following the main branch.** After each fetch, a newer commit is scanned once. The fingerprint covers only what the person reviews: library nicknames and paths, path variables and their folders, model folders, lib tables and `.kicad_dbl` files, never counts or per-file doubts. If it is the same, the profile moves to that commit silently, so a new footprint with its 3D model asks for nothing. If it differs, the row says "The library changed since you reviewed it." and offers "Review again". The layout reviewed before stays in use meanwhile, and a fetch with no newer commit scans nothing.
- **The Libraries browser.** Each linked team's reviewed libraries form a group after ours, with the team's mark and the repo's name. They are written out of the copy into `library-layouts/<key>/<commit start>/`, once per commit, in batches on a thread of their own, one writer per repo. The browser answers at once: the group says its files are being got ready, and the browser keeps asking until they are. When a newer commit's files are ready, the folder the browser had before is kept until it asks again, then deleted. This works offline. 3D models stay in the copy. A client library's items are drawn from these files.
- **The resolver.** A reference `LIB:NAME` is looked up in a profile, then in KiCad's installed libraries, with exact case for the file a table row names. Our own references resolve through the default profile. `LibraryResolver::with_source` resolves through a client profile, whose libraries come from the repo's lib tables, so a nickname that differs from its file name finds the library KiCad would. Nothing resolves client references yet; kicad-parts-02fb and kicad-parts-92cb will.

## Considered options

- **Rename client libraries with a prefix, such as `AC-Passives`.** Rejected: the client's boards store the old names and would break.
- **A short name per repo in the app.** Dropped after review: no feature used it, and the team's mark already tells repos apart.
- **Scan the person's own checkout.** Rejected: it may hold changes not committed, and the app never reads or writes a person's work (mx-70700f).
- **Ask the person to describe each repo by hand.** Rejected: most repos scan right, and hardware engineers should only fix what the scan got wrong.
- **Read the person's own KiCad lib tables for a client repo.** Not now: they describe one computer, not the repo. The resolver still does not read them; see Consequences.
- **Keep profiles on the team server.** Later: sharing profiles with teammates through the team server is a next step.

## Consequences

- `crates/catalog-browser/src/library_repos/layout/` holds the scan (`scan.rs`: `read_contents` reads in batches, and `scan` is one pure function over a file list and those contents), the store (`store.rs`), the browser's files (`files.rs`) and `Layouts`, which `LibraryRepos` uses.
- The library check and Add part still read only our own layout, through the default profile. kicad-parts-02fb and kicad-parts-ff3c extend them to client profiles. Choosing an item for a part leaves team groups out until copying between teams arrives (kicad-parts-1a46).
- `models_by_library` says where a footprint's own 3D model goes; only our layout has one. kicad-parts-02fb works out such rules for client repos.
- The import's own reading of model links (`classify_model_reference`) still follows the CSV catalog oracle, and keeps reading the older `${GITPLM_3DMODELS}` name. The library check does not, as before.
- **Known gaps:** the scan does not check a model link through `${KIPRJMOD}` or an absolute path. A lib table row whose path leaves the repo is skipped. A `.lib` file is told apart by its extension only. The resolver does not read the person's own lib tables, so a person's table that remaps a KiCad nickname is still not followed (kicad-parts-e83f).
